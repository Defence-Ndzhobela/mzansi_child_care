3Project Overview

Mzansi ChildCare is a Child Maintenance Management System. This document describes its PostgreSQL database: the structure of every table, the constraints and triggers that protect data, and the workflows the schema supports. It is written for a database developer or assessment panel who needs to understand the whole design without reading the SQL script.

4Database Architecture Overview

The schema is organised in five functional domains around a single identity table. Every domain references users; the child-centred domains also reference children.

4.1 Design principles visible in the script

PrincipleHow the script applies it
Surrogate UUID keysEvery business table uses id UUID PRIMARY KEY DEFAULT gen_random_uuid().
Closed vocabulariesStatus, role, method and type columns are VARCHAR with CHECK ... IN lists rather than PostgreSQL ENUM types.
Controlled deletionFinancial, messaging and identity references use ON DELETE RESTRICT; child-owned working data uses CASCADE; optional audit pointers use SET NULL.
Composite foreign keysPayments must agree with their arrangement on child, payer and receiver. Confirmations must be made by the payment's receiver. Optional arrangement links on assignments and conversations must agree on child.
Partial unique indexesBusiness rules that apply only in a state (one ACTIVE arrangement, one ACTIVE social worker per child, one PENDING link request) are expressed as UNIQUE ... WHERE indexes.
Triggers for row-level historyOnly the messages table uses triggers, to restrict inserts and updates.
Atomic installationThe script runs in one BEGIN ... COMMIT transaction, so a failed install leaves no partial schema.

4.2 ON DELETE behaviour by table

BehaviourWhere usedRationale
RESTRICTcreated_by, paying/receiving users, uploaded_by, reviewed_by, social_worker_id, assigned_by, sender_id; payments → children and arrangements; conversations → users and children; messages → conversationsProtects financial, assignment and messaging history from accidental deletion.
CASCADEfamily_relationships, child_link_requests, maintenance_arrangements, social_worker_assignments, professional_notes → children; payment_evidence, payment_reviews, payment_confirmations → paymentsRemoves dependent working data with its owner.
SET NULLchildren.archived_by, child_link_requests.reviewed_by, social_worker_assignments.ended_by; the arrangement link on assignments and conversations (column list SET NULL)Keeps the row when an optional pointer disappears.
Interaction to note. A child that has payments or conversations cannot be deleted (RESTRICT), even though several other child-owned tables use CASCADE. Deleting a child therefore only succeeds when no payments and no conversations exist for it.

5Database Technology and Tools

ComponentDetail
Database enginePostgreSQL 15 or later (stated in the script header).
Why 15+The script uses ON DELETE SET NULL (column_list) on two composite foreign keys. The column-list form was introduced in PostgreSQL 15.
Extensionpgcrypto is created with CREATE EXTENSION IF NOT EXISTS. The script itself calls only gen_random_uuid(), which is built into PostgreSQL core since version 13; no other pgcrypto function is used in the script.
Procedural languagePL/pgSQL, for the two trigger functions.
Key data typesUUID, VARCHAR(n), CHAR(n), TEXT, BOOLEAN, DATE, TIMESTAMPTZ, DECIMAL(12,2) (exact numeric for money), JSONB.
Time handlingAll timestamps are TIMESTAMPTZ with DEFAULT NOW(); dates without time use DATE.
CurrencyFixed to ZAR by CHECK on arrangements and payments.
Migration toolingThe script comment refers to npm run db:migrate, indicating a Node.js based migration runner that reads schema_migrations. The runner itself is not part of the supplied script.
Installation scopeFor a new, empty database only. It equals migrations 001–007 applied in sequence.

5.1 Data-type choices

ChoiceReason / consequence
DECIMAL(12,2) for amountsExact arithmetic, up to 9,999,999,999.99, two decimals. Avoids floating-point rounding.
CHAR(64) for the lookup hashA SHA-256 digest in hexadecimal is exactly 64 characters; fixed width suits it.
CHAR(3) for currencyISO-4217 style three-letter code, currently restricted to ZAR.
VARCHAR + CHECK instead of ENUMAdding a value only requires replacing a CHECK constraint, not altering a type.
JSONB for archived_familyFlexible snapshot with no fixed relational structure; not constrained by the script.

PostgreSQL composite foreign keys use the default MATCH SIMPLE behaviour: if any referencing column is NULL the constraint is not checked. On the two optional links this is the intended effect (no arrangement, no check). On payments and confirmations every column is NOT NULL, so the checks always apply.

13Functions and Triggers

The script defines two PL/pgSQL functions and two row-level BEFORE triggers, all on messages. Both raise exceptions with SQLSTATE 23514 (check_violation), so applications can treat them like CHECK failures.

13.1 Source of the functions and triggers

CREATE OR REPLACE FUNCTION enforce_message_sender() RETURNS trigger AS $$
BEGIN
    IF NOT EXISTS (
        SELECT 1 FROM conversations c
        WHERE c.id = NEW.conversation_id
          AND NEW.sender_id IN (c.parent_user_id, c.social_worker_id)
    ) THEN
        RAISE EXCEPTION 'The sender must take part in the conversation.' USING ERRCODE = '23514';
    END IF;
    RETURN NEW;
END
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_messages_enforce_sender
    BEFORE INSERT ON messages
    FOR EACH ROW EXECUTE FUNCTION enforce_message_sender();

-- Sent messages cannot be edited, and a read message cannot become unread.
CREATE OR REPLACE FUNCTION protect_message_history() RETURNS trigger AS $$
BEGIN
    IF NEW.conversation_id IS DISTINCT FROM OLD.conversation_id
       OR NEW.sender_id IS DISTINCT FROM OLD.sender_id
       OR NEW.message IS DISTINCT FROM OLD.message
       OR NEW.created_at IS DISTINCT FROM OLD.created_at THEN
        RAISE EXCEPTION 'Sent messages cannot be edited.' USING ERRCODE = '23514';
    END IF;
    IF OLD.is_read AND NOT NEW.is_read THEN
        RAISE EXCEPTION 'A message that was read cannot be marked unread.' USING ERRCODE = '23514';
    END IF;
    RETURN NEW;
END
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_messages_protect_history
    BEFORE UPDATE ON messages
    FOR EACH ROW EXECUTE FUNCTION protect_message_history();

21Conclusion

The Mzansi ChildCare schema is a coherent, well-constrained relational design. It uses 13 business tables centred on users and children, 33 foreign keys (five of them composite), 29 CHECK constraints, 7 unique constraints, 44 explicit indexes and two triggers. Its strongest features are:

  • Composite foreign keys that make payments agree with their arrangement and restrict confirmation to the receiving parent.
  • Partial unique indexes that express state-based business rules: one active arrangement, one active social worker per child, one pending link request.
  • A privacy-conscious child identifier: a keyed HMAC lookup hash instead of the national ID number.
  • Triggers and CHECK constraints that keep message history and read state trustworthy.

The principal gaps are not defects in the implemented rules but areas deliberately left to the application: role-aware validation, approval-flow enforcement, payment status consistency and database-level authorisation. Section 20 lists these as recommendations, with the schema left unchanged. Together with the documented workflows, this document should allow a reader to understand and review the complete database architecture without reading the original SQL.
